# Уведомления и раздел разработчика

## Включение тестов

В системном меню приложения (рядом с меню Apple) выберите **Show Developer Menu**.
Откроется раздел настроек **Разработчик**. **Hide Developer Menu** скрывает его,
в том числе из поискового индекса. Видимость не сохраняется между запусками.

Для каждого AppNotificationEvent есть отдельная кнопка теста: успешная загрузка,
ошибка загрузки, запуск/остановка сервера, критическая ошибка, обновление TorrServer.
Тесты вызывают тот же NotificationController.send, что и реальные события, с явно
помеченным примером содержимого. Изменять состояние сервера, файлы или обновления
они не могут. Выключенный общий переключатель или тип события подавляет и тест;
причина выводится под соответствующей кнопкой. Настройка звука также учитывается.

## Разрешение и результат — разные состояния

notificationsEnabledKey хранит намерение пользователя отправлять уведомления.
Его меняет только явное действие пользователя; системный запрет не стирает его.
Разрешение macOS хранится отдельно в NotificationSystemState и обновляется при
запуске, возвращении приложения на передний план, ручном обновлении статуса и
перед современной отправкой. Старые асинхронные ответы после изменения
переключателя отбрасываются. Отключение приложения/события во время проверки
также учитывается перед отправкой.

Подписанные командной подписью сборки используют UNUserNotificationCenter:
- включение при notDetermined запрашивает alert/sound;
- при denied доступна кнопка открытия системных настроек;
- ошибка авторизации отображается, ошибка отправки возвращается вызывающему коду,
  видна в настройках и записывается в OSLog с приватным текстом;
- успешный add означает принятие запроса системой, а не гарантию видимого баннера;
- foreground presentation включает banner/list/sound; отсутствие content.sound
  при выключенном звуке сохраняется.

Для локальной проверки современного API соберите приложение с установленным
сертификатом Apple Development, указав имя или SHA-1 сертификата из
`security find-identity -v -p codesigning`:

```sh
CODE_SIGN_IDENTITY='<identity>' ./scripts/build-app.sh
```

В Developer нажмите **Разрешить уведомления**, если разрешение ещё не запрошено.
При уже выданном отказе измените разрешение через **Открыть настройки macOS**.
Это подпись для локального тестирования, а не подписанный Developer ID и
нотарифицированный релиз для распространения.

Без CODE_SIGN_IDENTITY build-app.sh сохраняет ad-hoc подпись. Для совместимости
в такой сборке остаётся legacy API:
- публичного надёжного API чтения разрешения у него нет; статус **неизвестно**,
  переключатель не выдаётся за подтверждение разрешения;
- deliver() не считается успешной доставкой;
- подтверждение отслеживается через NSUserNotificationCenterDelegate.didDeliver;
- если за 3 секунды подтверждения нет, результат — **доставка не подтверждена**,
  а не успех и не доказанный отказ системы;
- даже didDeliver не доказывает, что пользователь увидел баннер.

Стабильная подпись Apple и ручная проверка на macOS необходимы для окончательной
проверки системного поведения. Focus, стиль предупреждений и звук управляются macOS.
Приложение не обходит системное разрешение и не читает частную базу разрешений.

## Проверки

`./scripts/verify-notifications.sh` проверяет алгоритм блокировки, сохранение
переключателей/звука, названия и безопасное содержимое всех шести тестов, а также
наличие сообщений для всех результатов. Требуется Swift compiler; тест не отправляет
уведомления. `./scripts/verify-settings-search.sh` проверяет алгоритм поиска.

На Mac дополнительно:
1. Собрать .app через scripts/build-app.sh и запустить именно bundle.
2. Проверить, что до Show Developer Menu раздела нет и поиск его не показывает.
3. Открыть developer-раздел; при выключенных уведомлениях получить «выключены».
4. Включить уведомления в «Основные», проверить отдельный статус разрешения.
5. При разрешённых уведомлениях отправить каждый из шести тестов. Проверить баннер,
   текст, звук и сообщение результата. Сервер/загрузки не должны изменяться.
6. Выключить один тип события: его тест подавляется, другие продолжают отправляться.
7. Выключить звук и проверить отсутствие звука у нового теста.
8. Запретить уведомления в macOS и вернуться в приложение: современный статус
   обновляется; в legacy режиме статус остаётся честно неизвестным. Проверить тест.
9. Снова разрешить их в macOS: намерение приложения включать уведомления сохраняется.
10. Проверить отказ/ошибку авторизации на сборке со стабильной подписью, Focus,
    отсутствие подтверждения legacy, Hide Developer Menu и повторный запуск.

В Linux выполнены синтаксический разбор исходников Swift и bash, git diff --check
и статическая проверка подключения всех событий и скрытия developer-раздела.
Swift compiler/macOS SDK здесь отсутствуют: компиляция, исполнение Swift-проверок
и реальная доставка уведомлений в этой среде не проверялись.
